# 实现架构

## 每日流水线

`抓取职位 → 标准化 → 去重 → 硬条件过滤 → 语义评分 → Top 10 → 生成材料 → 人工确认 → 填表`

### 1. 抓取与标准化

首批适配 Greenhouse、Lever 和 Ashby 的公开职位接口。每条职位统一为 `company`、`title`、`location`、`salary`、`description`、`sourceUrl`、`externalId`、`publishedAt` 和 `source`。

Dashboard 在浏览器状态恢复后立即刷新，并在页面可见期间每 5 分钟刷新一次；重新切回标签页也会触发刷新。新请求会取消旧请求，只有最新请求可以提交状态。已有结果会保留到刷新成功，已加入申请队列的岗位不会因来源下架而消失。

扫描 API 对每个公司职位板独立容错。只要至少一个来源成功，就返回健康来源的结果并通过 `failures` 暴露部分故障；全部失败时返回 503。响应使用 `Cache-Control: no-store` 并携带 `fetchedAt`。

LinkedIn 不属于自动抓取适配器。应用构造并在 Dashboard 展示已保存的搜索 URL，不读取 Cookie、不操作已登录页面，也不会把搜索入口声称为已抓取或已评分的职位。用户可明确选择粘贴职位链接与完整描述；应用仅对这份用户提供的数据运行本地规则评分，并以“LinkedIn · 用户导入”记录来源。

### 2. 去重与硬条件

使用来源 ID 和“公司 + 标准化职位名 + 地点”的指纹去重。地点、签证、最低薪资、职级和黑名单属于硬条件，不满足的职位不进入模型评分。

### 3. 匹配评分

建议总分 100：技能/职责 35，经历证据 25，职级 15，地点与工作方式 10，薪资 10，个人偏好 5。评分结果必须附带引用自简历或职位描述的理由，不能只给关键词相似度。

### 4. Top 10 与材料

每天只处理新出现且达到阈值的前 10 个职位。材料生成只能重排和改写已存在的经历，不得虚构技能、数字或雇佣事实。

### 5. 自动填表边界

浏览器层使用按 ATS 划分的适配器。姓名、联系方式、简历上传等确定字段可以自动填写；自愿披露、薪资预期、签证、犯罪记录、开放题和验证码必须按个人规则或转交用户。最终提交默认需要人工确认，并保留页面截图、填写内容和时间戳。

### 6. 职业教练与路线图

职业教练把简历明确写出的内容作为事实边界，通过追问项目背景、个人行动、结果证据和兴趣来验证方向。用户可以挑战当前目标或探索转行。每轮 AI 对话同时返回 3–5 个阶段的学习路线，每阶段包含可验证结果与实践项目；没有 API Key 时，本地模式仍提供问题框架和 12 周基础路线。

## 下一阶段模块

- `sources/`：职位源适配器
- `scoring/`：硬条件、匹配评分和解释
- `profile/`：简历事实库与偏好
- `applications/`：申请状态、材料版本和审计记录
- `automation/`：每日调度与浏览器填表
- `app/`：本地操作界面

## 交付流水线

协作分支与 Pull Request 使用 GitHub Actions 执行 `npm ci` 和 `npm run check`。`main` 或手动运行会额外重建纯静态 Demo，并确认仓库中的 `live-demo/` 与源码一致。GitHack 直接从公开 GitHub 文件提供预览，不调用 Pages API。静态构建设置 `VITE_STATIC_DEMO=true`，跳过后台实时扫描并明确标记演示状态；无需部署凭据。

## 本地 API Key 边界

用户通过本地测试窗口提交的 OpenAI Key 会先调用模型读取接口验证权限，随后只保存在当前服务进程的内存中。设置和移除临时 Key 的接口拒绝非 loopback 主机请求；浏览器存储、Cookie、日志和仓库均不保存 Key。GitHub 静态 Demo 不运行该服务端接口，也不接收 API Key。
